BIZ-STRIVES — COMPLETE DEVELOPMENT PHASES
=============================================

Project Vision
--------------
BIZ-STRIVES is a scalable business finance management platform.

The first version is for personal use, but the architecture must support
multiple businesses and users in the future.

IMPORTANT CORE PRINCIPLE:
BIZ-STRIVES is NOT a complicated double-entry accounting/ERP system.

The core financial engine must remain simple:

    TOTAL MONEY RECEIVED
    - BUSINESS EXPENSES
    - PERSONAL SPENDING
    = MONEY REMAINING

Savings/reserved money is NOT treated as an expense. It is money allocated
and reserved from available funds.

The platform should feel simple enough for a small business owner to use
every day while being architected cleanly enough to become a SaaS product.

============================================================
PHASE 0 — PROJECT FOUNDATION & ARCHITECTURE
============================================================

Goal:
Create the technical foundation before building major features.

Requirements:
- Platform name: BIZ-STRIVES
- Business/workspace name is configurable from the dashboard.
- Initial business can be "Klassiq Grafikz", but the platform itself must
  remain generic.
- Design for multi-user/multi-business support from the beginning.
- Do not make the core system dependent on Supabase.
- Frontend may be deployed on Vercel or another suitable platform.
- Backend/database should be independently controlled.
- Prefer a self-hostable architecture.

Recommended stack:
- Frontend: Next.js + React + TypeScript
- Styling: Tailwind CSS
- Backend: Node.js with NestJS or a clean modular Node.js API
- Database: PostgreSQL
- ORM: Prisma or Drizzle
- Background jobs: Redis + BullMQ or equivalent
- File storage: S3-compatible object storage
- Email: transactional email provider with API
- PDF generation: server-side PDF generation
- Authentication: secure session/JWT architecture
- Deployment: Docker-friendly/Vercel/appwrite/render/netflify

Architecture principles:
- Modular backend
- REST API or well-structured API layer
- Strong validation
- Centralized error handling
- Audit logging for important financial changes
- Database migrations
- Environment variables for secrets
- No financial secrets hard-coded
- Secure authentication
- User/business data isolation
- Automated database backups
- Logging and monitoring

============================================================
CRITICAL BUSINESS RULES
============================================================

RULE 1:
The financial engine must remain simple.

    MONEY RECEIVED
    - BUSINESS EXPENSES
    - PERSONAL SPENDING
    = MONEY REMAINING

RULE 2:
Savings allocations are reserved funds, not business expenses.

RULE 3:
Account transfers are not income or expenses.

RULE 4:
Every financial transaction must have a real transaction date.

RULE 5:
Historical monthly reports must be reconstructable from individual
transactions.

RULE 6:
Changing the current date/month must never alter historical records.

RULE 7:
Closed months must be protected from accidental changes.

RULE 8:
Currency must be stored with every financial transaction.

RULE 9:
Location detection can suggest currency but must never silently modify
existing records.

RULE 10:
Customer payments should be connected to customers/projects whenever
possible.

RULE 11:
Invoices may initially be sent manually.

RULE 12:
Bank transaction detection is a future integration and must not be
required for the core financial system.

RULE 13:
The website notification about detected money should ask the user what
the money is for rather than automatically guessing.

RULE 14:
The application must remain simple enough for a small business owner.

RULE 15:
The database must be designed for multiple businesses even if the first
deployment has only one business.

DEVELOPMENT INSTRUCTIONS FOR OPENCODE
============================================================

Build BIZ-STRIVES incrementally.

Do NOT generate the entire application in one huge step.

For each phase:

1. Inspect the existing project.
2. Plan the implementation.
3. Create/update database schema.
4. Create migrations.
5. Build backend functionality.
6. Build frontend UI.
7. Add validation.
8. Add tests.
9. Run tests.
10. Fix errors.
11. Verify existing features still work.
12. Document the completed phase.
13. Only then move to the next phase.

Never destroy existing working functionality to implement a new feature.

Use clean modular architecture.

Prefer reusable components.

Keep financial calculations centralized in one financial service/module so
that the same calculations are used by:
- Dashboard
- Reports
- Monthly records
- Statements
- Notifications
- Exports

Avoid duplicating financial formulas throughout the codebase.
